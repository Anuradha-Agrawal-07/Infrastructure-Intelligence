# TaskFlow — Project & Task Management (Test Application)

A small, realistic project/task management web app used as a **standalone test
application**: a polyglot microservice system with real inter-service network
communication, real PostgreSQL and Redis usage, JWT auth, and a working React
frontend. It intentionally contains **no monitoring, discovery, telemetry, or
anomaly-detection code** — this app is meant to be observed by an external
tool, not to observe itself.

## Architecture

```
Frontend (React, served on :3000)
   |
   v
API Gateway (FastAPI, :8000)
   |
   +--> Auth/User Service (FastAPI, :8001) --> PostgreSQL (:5432)
   |
   +--> Task Service (FastAPI, :8002) --> PostgreSQL (:5432)
   |
   +--> Notification Service (Go, :8003) --> Redis (:6379)
```

- The **browser only ever talks to the API Gateway**. It never calls Auth,
  Task, or Notification services directly.
- The **API Gateway** is the only service that talks to the other three
  services. It does this over real HTTP calls to their container hostnames
  (`auth-service`, `task-service`, `notification-service`) inside the Docker
  network — not in-process calls, not shared code.
- **Auth/User Service** and **Task Service** each own their own tables in the
  same PostgreSQL instance (`users` and `tasks` respectively) and talk to it
  via SQLAlchemy over a real TCP connection to the `postgres` container.
- **Notification Service** is written in **Go** (the one service with a
  different language than the rest of the stack) and stores/reads
  notifications exclusively in **Redis**, via `go-redis`, as JSON blobs in a
  per-user list (`notifications:user:<id>`).
- On every authenticated request, the API Gateway calls
  `POST /verify` on the Auth/User Service over the network to validate the
  bearer token — this is a real, continuous runtime dependency, not just a
  one-time login-time call.

### Why this stack

The stack is deliberately **not** a typical Node.js/Express monolith:

| Layer | Technology |
|---|---|
| Frontend | React (Vite) |
| API Gateway | Python + FastAPI |
| Auth/User Service | Python + FastAPI |
| Task Service | Python + FastAPI |
| Notification Service | **Go** (net/http + go-redis) |
| Database | PostgreSQL |
| Cache / message store | Redis |

## Prerequisites

- Docker and Docker Compose (Docker Desktop, or `docker` + `docker compose`
  plugin on Linux)
- No other local dependencies are required — Python, Node, and Go all run
  inside their respective containers.

## Setup — exact commands

From the project root (the directory containing `docker-compose.yml`):

```bash
docker compose build
docker compose up -d
```

This builds and starts 7 containers: `postgres`, `redis`, `auth-service`,
`task-service`, `notification-service`, `api-gateway`, `frontend`.

Check that everything is healthy:

```bash
docker compose ps
```

Watch logs for any service if needed:

```bash
docker compose logs -f api-gateway
docker compose logs -f notification-service
```

Open the app in a browser:

```
http://localhost:3000
```

To stop everything:

```bash
docker compose down
```

To stop and wipe the database volume (fresh start):

```bash
docker compose down -v
```

## Using the app (manual workflow via the UI)

1. Open `http://localhost:3000`.
2. Click **Register**, create a user (e.g. `alice` / `alice@example.com` /
   a password of 6+ characters). You'll be logged in automatically.
3. Open a second browser (or an incognito window) and register a second user,
   e.g. `bob`.
4. As `alice`, click **+ New Task**, give it a title, and assign it to `bob`.
5. As `bob`, open the **Notifications** button in the header — you'll see the
   assignment notification that was generated by the Notification Service and
   stored in Redis.
6. As `bob`, mark the task **Done** — `alice` will receive a completion
   notification in her own Notifications panel.

## Testing the workflows via curl (exact commands)

These commands exercise the full path: browser-equivalent request → API
Gateway → downstream service → database/cache, exactly as the UI does.

```bash
BASE=http://localhost:8000

# 1. Register two users (API Gateway -> Auth/User Service -> PostgreSQL)
curl -s -X POST $BASE/api/auth/register -H "Content-Type: application/json" \
  -d '{"username":"alice","email":"alice@example.com","password":"secret123","full_name":"Alice Manager"}'

curl -s -X POST $BASE/api/auth/register -H "Content-Type: application/json" \
  -d '{"username":"bob","email":"bob@example.com","password":"secret123","full_name":"Bob Engineer"}'

# 2. Log in as alice (API Gateway -> Auth/User Service -> PostgreSQL)
ALICE_TOKEN=$(curl -s -X POST $BASE/api/auth/login -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"secret123"}' | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

# 3. Confirm the token by calling a protected route
#    (this triggers a live API Gateway -> Auth/User Service /verify call)
curl -s $BASE/api/users/me -H "Authorization: Bearer $ALICE_TOKEN"

# 4. List users (for picking an assignee)
curl -s $BASE/api/users -H "Authorization: Bearer $ALICE_TOKEN"

# 5. Create a task assigned to bob (id=2)
#    (API Gateway -> Task Service -> PostgreSQL, then
#     API Gateway -> Notification Service -> Redis)
curl -s -X POST $BASE/api/tasks -H "Authorization: Bearer $ALICE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Set up CI pipeline","description":"Add GitHub Actions","assignee_id":2}'

# 6. Log in as bob and check his notifications
BOB_TOKEN=$(curl -s -X POST $BASE/api/auth/login -H "Content-Type: application/json" \
  -d '{"username":"bob","password":"secret123"}' | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

curl -s $BASE/api/notifications -H "Authorization: Bearer $BOB_TOKEN"

# 7. Bob marks the task done (triggers a completion notification back to alice)
curl -s -X PATCH $BASE/api/tasks/1 -H "Authorization: Bearer $BOB_TOKEN" \
  -H "Content-Type: application/json" -d '{"status":"done"}'

curl -s $BASE/api/notifications -H "Authorization: Bearer $ALICE_TOKEN"
```

### Verifying real database/cache usage directly

```bash
# PostgreSQL: confirm both services' tables exist and are populated
docker compose exec postgres psql -U appuser -d appdb -c "\dt"
docker compose exec postgres psql -U appuser -d appdb -c "SELECT id, username, email FROM users;"
docker compose exec postgres psql -U appuser -d appdb -c "SELECT id, title, status, assignee_id FROM tasks;"

# Redis: confirm the notification actually landed in Redis (not just in a response body)
docker compose exec redis redis-cli LRANGE notifications:user:2 0 -1
```

## Notes on scope

- Auth and Task services share one PostgreSQL instance but own separate
  tables — a common "shared database, per-service tables" pattern for small
  systems. Neither service reads the other's tables directly; all
  cross-service data flow goes back through the API Gateway.
- The Notification Service has no database of its own — Redis is its only
  persistent store, matching the required Notification Service → Redis edge.
- This app does not include and does not integrate with any monitoring,
  discovery, or observability agent. It is meant to be a target for one, not
  to contain one.
